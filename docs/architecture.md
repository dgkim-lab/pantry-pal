# Pantry Pal — Architecture and Data Model

## Runtime

The application is a single Next.js service:

- Server-rendered and client UI through the App Router
- Route handlers/server actions for authenticated application operations
- Prisma as the PostgreSQL data-access layer
- Generic OIDC login through an authentication adapter, configured by environment variables
- PWA manifest and service worker for installability and static asset caching

The browser must have network access for application reads and writes in the initial release.

## PostgreSQL naming conventions

The database uses plural `snake_case` table names and `snake_case` column names for direct SQL readability, while Prisma models and application properties remain idiomatic camelCase. All primary keys and foreign keys use PostgreSQL `uuid` values generated by the database.

## Security boundaries

1. The authentication layer validates the OIDC session.
2. Every server operation resolves the current user.
3. Every household/list/item query is constrained by membership, never by an ID alone.
4. Role checks apply to mutations such as invitations, list deletion, checkout, and catalog management.
5. OIDC secrets and database credentials are read only from environment variables.

## Recommended entities

### Identity and collaboration

- `User`: internal ID, OIDC subject, email, display name, timestamps.
- `Household`: name, owner, timestamps.
- `HouseholdMember`: household, user, role, invited/accepted timestamps; unique on household and user.
- `ShoppingList`: household, name, status, timestamps.

### Catalog and planning

- `Category`: household-scoped optional category name.
- `Store`: household, name, type (`LOCAL` or `ONLINE`), optional address/URL/notes.
- `MasterItem`: household, name, optional category/brand/preferred store, default quantity/unit, capacity/unit, default price/currency, notes.
- `ShoppingListItem`: list, optional master item, copied name/brand/quantity/unit/capacity/unit/notes, status, checked-at, timestamps.

The copied fields are intentional denormalization: list planning and historical views remain stable when a master item is edited.

### Cart and history

- `Cart`: household, source shopping list, status (`ACTIVE`, `CHECKED_OUT`, `CANCELLED`), store, timestamps.
- `CartItem`: cart, optional source list item/master item, copied editable item fields, expected/actual price, quantity, capacity, notes.
- `Purchase`: household, source cart, store, purchased-at, currency, total price if supplied, notes.
- `PurchaseItem`: purchase, optional master item, immutable snapshot of name/brand/quantity/unit/capacity/unit/actual price/currency, notes.

Purchase-item snapshots must not be derived dynamically from the current master item.

## Important invariants

- A list item can be checked into the active cart at most once unless the user explicitly restores/reopens it.
- Checkout is transactional: a purchase and all purchase items are created together, and the cart is marked checked out only if all records succeed.
- A checked-out cart cannot be edited; corrections should use an explicit adjustment flow in a later version.
- Deleting a master item must not delete shopping-list, cart, or purchase snapshots.
- A household member can access only household-owned lists, stores, catalog items, carts, and purchases.
- Currency is stored on every monetary record that needs historical fidelity.

## Suggested indexes

- `User.oidcSubject` unique
- `HouseholdMember (householdId, userId)` unique
- `MasterItem (householdId, normalizedName)` for autocomplete
- `ShoppingListItem (listId, status)`
- `Cart (householdId, status)`
- `Purchase (householdId, purchasedAt)`
- `PurchaseItem (masterItemId, purchasedAt)` where supported by the ORM/database strategy

## OIDC configuration

Support both providers through standard OIDC settings rather than provider-specific application logic:

```dotenv
OIDC_ISSUER_URL=https://identity.example.com/realms/pantry
OIDC_CLIENT_ID=pantry-pal
OIDC_CLIENT_SECRET=change-me
OIDC_SCOPE=openid profile email
AUTH_SECRET=change-me
APP_URL=https://pantry.example.com
```

Keycloak can use a realm issuer URL. Cognito can use its user-pool issuer URL. The callback URL should be derived from `APP_URL` and documented for the selected provider.

## Environment contract

```dotenv
DATABASE_URL=postgresql://user:password@postgres:5432/pantrypal
DIRECT_URL=postgresql://user:password@postgres:5432/pantrypal
AUTH_SECRET=change-me
OIDC_ISSUER_URL=
OIDC_CLIENT_ID=
OIDC_CLIENT_SECRET=
OIDC_SCOPE=openid profile email
APP_URL=http://localhost:3000
DEFAULT_LOCALE=en
DEFAULT_TIMEZONE=Asia/Seoul
DEFAULT_CURRENCY=KRW
```

`.env` is local/private configuration and must not be committed. `.env.example` should contain names and safe placeholders only.
